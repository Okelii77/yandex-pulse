# Stage 2 — experimental only

All code below is loopback/synthetic, no credentials or Yandex requests. The branch has no production deploy. The benchmark compares the original scheduling model with optimized Python/Go/Node/Rust (same 25 requests, 8 concurrent, HTTP/1.1, no keep-alive; baseline has 27 requests). Rust reqwest blocking uses a fixed 8-thread pool, scheduling differs between clients. 100 repetitions per delay 0/30ms; GNU time records CPU/RSS, with 10ms CPU resolution, subprocess cold wall time includes launch and measurement overhead; not host/server metrics. Compilation time and binary/script sizes separate; interpreted runtime sizes not included. Cargo.lock generated and uploaded; commit the resolved lock before final repeatability claims.

Core candidates implement public HTTP/TLS status classification for local fixtures only. Authenticated operations explicitly unsupported, no replacement or production integration. Rust lacks checked_at in the current prototype. DNS failure injection, full timeout semantics, HTTP/2, auth, complete schema parity and reconnect not proven. Ynison Rust client is a local state-stage experiment, not complete redirector or production gate integration; never point it at Yandex. Shared fixtures verify raw state validation and server cooldown handling. History tests use local SQLite, not D1; exact rolling cutoff means reuse only at same epoch, production revision invalidation still needs work. Scheduler is a pure decision model, not a distributed lock.

CI evidence is required before asserting Rust builds or benchmark results. Never publish to main or deploy. No costs authorized.
